# Impact Replay: honest backtests for decision-flow edits

**Live demo:** https://mohith26.github.io/taktile-policy-impact-replay/

An unofficial concept for a new panel in a decision-flow canvas (built with Taktile's product in mind). Before a risk team publishes an edited credit flow, Impact Replay replays the logged application history through the published version and the draft and answers three questions a plain backtest can't:

1. **Which edit caused which flip?** Exact Shapley attribution of approvals and expected loss across all edits in the draft, plus the number of flips that only happen when two or more edits ship together.
2. **How risky are the applicants the draft newly approves?** Their outcomes were never observed, because the old flow declined them. Impact Replay uses the logged approval propensity (a 10% randomised test-below-the-cut program) in a cross-fitted, doubly robust (AIPW) estimator with bootstrap intervals, instead of extrapolating a model fit on the booked book.
3. **What can't the history tell us?** Swap-ins from regions the old policy never explored (here, fraud-screen declines) get partial-identification bounds instead of a made-up point estimate.

It also reports approval-rate and adverse-impact-ratio shifts by group (with bootstrap intervals) and segment-level deltas.

## Why this is hard

A standard backtest scores swap-ins (applicants the new flow approves but the old one declined) with whatever model it has, usually one fit on loans that were actually booked. That book contains no applicants beyond the old cutoffs, so the model extrapolates exactly where the policy change lives. This is the reject-inference problem, and it is why a relaxed cutoff often looks cheaper in a backtest than it turns out to be in production.

If the lender logs the probability with which each historical application could have been approved (a test-below-the-cut or champion/challenger program gives you this for free), the problem becomes an off-policy evaluation problem with known propensities. AIPW combines an outcome model `m(x)` with an inverse-propensity correction:

```
phi_i = m(x_i) + A_i / pi_i * (Y_i - m(x_i))
```

`phi_i` is unbiased for the default probability of row i whenever `pi_i > 0`, even if `m` is wrong, and it reduces to the observed outcome when `pi_i = 1`. Every set-level number in the panel (swap-in default rate, expected loss change, segment deltas, Shapley loss shares) is a sum of `phi_i` terms, so they are all consistent with each other. Where `pi_i = 0` nothing identifies the outcome, so the panel reports a bound: worst case `[0, 1]` per applicant, tightened under an explicit monotonicity assumption (risk does not fall as device risk rises).

## What the demo data shows

Synthetic history of 40,000 applications (Jul 2024 to Jun 2025, 12-month performance) generated by `scripts/generate.mjs` (seeded). The true default model has risk that accelerates just past both historical cuts (DTI above 0.45, bureau score below 620) and thin-file risk driven by open-banking cash-flow volatility rather than bureau score. Age carries no risk, but young applicants are far more often thin-file.

On the demo seed, with the four default edits:

- Approval rate 62.5% to 75.4%; 5,428 swap-ins, 260 swap-outs; 539 flips need two or more edits together.
- Swap-ins from lowering the bureau cutoff: naive backtest 10.8% default, AIPW 14.3% (90% CI 8.5% to 21.2%), simulation truth 15.4%.
- The thin-file cash-flow route adds about 2,100 approvals at slightly negative expected loss and lifts the 18-24 adverse impact ratio from 0.78 to 0.92.

Repeated-simulation check (`node scripts/coverage.mjs 40`, 40 fresh datasets):

| | AIPW | Naive backtest |
|---|---|---|
| Bias, swap-in default rate (all 4 edits) | -0.01 pp | -0.61 pp |
| Bias, affordability-edit swap-ins | +0.69 pp | -3.34 pp |
| Bias, bureau-cutoff-edit swap-ins | -0.50 pp | -3.47 pp |
| 90% interval coverage, swap-in default rate | 90% | n/a |
| 90% interval coverage, expected loss change | 87.5% | n/a |

## How it works

- `core/replay.js` (ES module, runs in the browser and Node): flow execution, decision diff and node-to-node transitions, weighted ridge logistic regression (IRLS), cross-fitted AIPW pseudo-outcomes, a naive baseline, bootstrap intervals over applicants, exact Shapley values over edit subsets (2^k flow replays, k <= 5), fairness (adverse impact ratio with bootstrap CI), segment tables.
- `scripts/generate.mjs`: seeded generator for `data/applications.json` (what a lender would have: inputs, logged decision, propensity, outcomes for booked loans only) and `data/truth.json` (true default probabilities, used only for the simulation-check marker and tests).
- `index.html`, `app.js`, `style.css`: static UI, no build step. Every number on screen is computed in the browser from the data file.

## Run it

```
node scripts/generate.mjs          # regenerate data (seed 20250630)
node --test test/replay.test.mjs   # 10 tests
node scripts/coverage.mjs 40       # repeated-simulation bias/coverage check
python3 -m http.server             # then open http://localhost:8000
```

Tests cover flow semantics, edit immutability, logistic-regression recovery, the AIPW identity for always-approved rows, diff consistency, Shapley efficiency and null-player properties, bound behaviour for unexplored regions, and a multi-seed unbiasedness/coverage check against the naive estimator.

## Honest limitations

- Synthetic data. The size of the naive-vs-AIPW gap depends on how nonlinear risk is past the old cuts; on a real portfolio it could be smaller or larger.
- AIPW needs logged propensities. Without an exploration program (test-below-the-cut, randomised challengers), swap-in loss is only partially identified and the panel can only show bounds.
- Intervals are percentile bootstrap over applicants with the outcome model held fixed (cross-fitted once). Measured coverage is close to nominal here but can undercover with very few explored loans.
- Outcomes are a 12-month default flag with a fixed 65% LGD; no time-to-default, prepayment, pricing or take-up modelling.
- Shapley attribution is exact but exponential in the number of edits; beyond ~10 edits it would need sampling.
- The fairness view uses age band as an example protected attribute; real fair-lending analysis would use the lender's own groups (often proxy-based) and legal review.
